# Can you trust that this app was built from this source?

CodeRoamer is open source, and the App Store version is not something you compile yourself. That
gap deserves a straight answer rather than a badge.

The question this document answers is:

> The app on my phone says it was built from commit `eac4631`. How do I know that is true, and not
> a string somebody typed into a config file before uploading an entirely different build?

Short version: you can verify that **the artifact Apple received came from a specific public commit
through a specific public workflow run**, and that verification does not depend on trusting the
maintainer. You cannot verify **the copy installed on your device**, because iOS provides no way to
extract and hash it. Everything below is the detail behind those two sentences.

## Why the obvious approach proves nothing

The naive version of build provenance is: put the commit SHA in the app and show it on an About
screen. That is worth something — it catches the maintainer shipping the wrong branch, or a build
made from a dirty working tree — but as evidence it is circular. The About screen is generated by
the same build it claims to describe.

Concretely, here is how a dishonest release would work, using nothing but the tools any maintainer
already has:

1. Edit `app.config.js` so `gitCommit` returns a hardcoded, innocent-looking SHA.
2. Make whatever unpublished changes you like.
3. Build locally (`eas build --local`, or plain Xcode).
4. Upload with Transporter or `eas submit`, bypassing CI entirely.
5. Create a GitHub Release by hand, with release notes stating the innocent SHA.

The result passes every check that relies on the publisher's own output. The About screen shows the
wrong commit and looks perfectly normal. This is the scenario that any honest provenance story has
to address head-on.

## Who can attest to what

The way out is to stop asking the publisher and start collecting statements from parties who have
no reason to cooperate in a lie, and whose statements the publisher cannot forge.

| Party | What it independently knows | Can the maintainer forge it? |
| --- | --- | --- |
| The app itself | What its own config says | Yes, trivially |
| The maintainer's release notes | Whatever was typed | Yes, trivially |
| GitHub Actions | That a workflow ran, on which commit, and what it printed | No — run logs are public and immutable |
| Sigstore / GitHub OIDC | That a specific artifact was produced by a specific workflow, in a specific repo, at a specific commit | No — the signing identity is issued to the workflow, not to a person |
| Expo / EAS | Which git commit the build worker checked out, and which artifact it produced | Not without compromising Expo; the maintainer can *bypass* EAS but not make it lie |
| Apple | Which binary was uploaded, under which version and build number | No, but Apple tells you very little: TestFlight shows a version and build number, nothing about source |

The useful statements come from the middle rows. That is what this repo's release pipeline is built
around.

## The ladder

Provenance is not binary. These are the rungs, in order of how much they are worth:

| Rung | Mechanism | Catches | Status |
| --- | --- | --- | --- |
| 0 | "Built from `main`" in the README | Nothing | — |
| 1 | Commit SHA embedded in the app, shown in Settings → About | Accidental drift: wrong branch, dirty tree, unpushed commit | Done |
| 2 | CI refuses to publish unless the commit EAS reports equals the tagged commit | A build that CI itself produced from the wrong source | Done |
| 3 | Sigstore attestation signed by the workflow's OIDC identity | A release published by hand, claiming a commit it was not built from | Done |
| 4 | The shipped JavaScript bundle published as a release asset | A binary whose behaviour does not match the source you were shown | Done |
| 5 | Independent rebuild producing a byte-identical artifact | Everything above, plus a compromised build service | **Not achievable for the iOS binary** |

Rung 5 is what "reproducible builds" means in the Debian or Signal sense, and it is where iOS stops
being cooperative — see below.

## What you can check today

**1. The version and build number match a published release.**

TestFlight and the App Store show something like `1.5.0 (137)`. Every build this project ships
comes from a tagged workflow run that publishes a GitHub Release naming that exact build number. A
build number appearing in TestFlight with no corresponding release is itself the signal that
something was submitted outside the pipeline.

**2. The attestation verifies.**

Each release attaches `main.jsbundle` and attests both it and the submitted IPA:

```bash
gh release download v1.5.0 --repo oogxdd/coderoamer --pattern main.jsbundle
gh attestation verify main.jsbundle --repo oogxdd/coderoamer
```

This checks a Sigstore signature made with the identity GitHub issues to this repository's
workflow, recorded in a public transparency log. The maintainer cannot produce that signature on a
laptop, and cannot retroactively change what was claimed for a version that has already shipped.

**3. The code that runs is the code you can read.**

`main.jsbundle` is not a hash of something you have to take on faith — it is the actual JavaScript
extracted from the IPA that was submitted to Apple. Apple re-signs and FairPlay-encrypts the native
Mach-O binary, but leaves resources like this one untouched, so what ships is what is attached to
the release. You can read it, search it for anything that should not be there, and compare it
against the source at that commit.

Note the honest limit: do not expect a locally rebuilt bundle to hash identically. Metro's output
is not guaranteed byte-stable across machines and environments, so the bundle is *auditable* but
not yet *reproducible*. Making it reproducible is the single most valuable improvement left.

**4. The workflow run is public.**

Every release links its Actions run. The logs show EAS reporting which commit it built, and show
the job failing if that disagreed with the tag.

## What is still not covered

**A maintainer who bypasses CI entirely.** Apple does not require submissions to originate from
this repository. Someone holding an App Store Connect key can upload anything, from anywhere. What
they cannot do is make that build carry an attestation, or make a matching release appear with a
valid signature — so the fraud is detectable by anyone who looks, but only if they look. The
practical mitigation is to keep the App Store Connect API key exclusively in EAS, so no local
submission path exists at all.

**Verifying the app already installed on your device.** iOS does not let you extract and hash an
installed application. The object under verification is the artifact Apple received, not the one on
your phone. Bridging that last gap is up to Apple, and today nobody — not Signal, not anyone — can
close it on iOS.

**Everything upstream of the commit.** Provenance says the build came from commit `X`. It says
nothing about whether `X` is good code, or whether a dependency in `package-lock.json` is
trustworthy. That is a different problem (supply chain), addressed by review, pinned lockfiles, and
reading diffs.

So the strongest honest claim is:

> The binary Apple received was produced by GitHub Actions from this public commit. You are
> trusting GitHub, Expo, and Apple — but not the maintainer's laptop.

That is meaningfully stronger than an unsupported README claim, and meaningfully weaker than a
reproducible build you can check yourself.

## What would strengthen this further

In rough order of value per unit of effort:

- **A deterministic bundle recipe.** Pin the Node and Metro versions, document the exact command,
  and check in CI that building the bundle twice yields the same hash. Then anyone could rebuild
  from the tag and compare against the published hash, which is rung 5 for the part of the app that
  actually contains the product logic.
- **Signed tags.** `git tag -s` plus a signature check in the workflow, so the release trigger
  itself is attributable rather than "whoever could push a tag".
- **Branch protection with required review.** Provenance to an unreviewed commit is weaker than
  provenance to a reviewed one.
- **A public EAS project page**, so Expo's record of "build 137 came from commit X" is readable by
  third parties rather than only by the maintainer.
- **Publishing every build number, including abandoned ones**, so gaps in the TestFlight sequence
  are explainable rather than suspicious.

## For comparison

- **Debian, Tails, F-Droid**: full reproducible builds. A third party rebuilds from source and gets
  a byte-identical package. Possible because nobody re-signs the artifact after the fact.
- **Signal on Android**: publishes a documented Docker-based procedure to rebuild the APK and
  compare it against the Play Store copy. Possible because Android lets you pull the installed APK
  off the device.
- **Signal on iOS**: does not offer this, for exactly the reasons above.
- **CodeRoamer**: attested provenance for the submitted artifact, plus publication of the shipped
  JavaScript. Rungs 1–4, not 5.

If that distinction matters for your use, the honest recommendation is to run the app from source —
`npx expo run:ios` against a checkout you have read — rather than the App Store build.
