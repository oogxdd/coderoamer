## The key realization

There are **two different "sessions"** on a sprite, and the desktop commands you like hit each one:

| Desktop | What it actually reads | Lives where |
|---|---|---|
| `claude --resume` → history picker | Claude's own **transcripts** (`~/.claude/projects/<cwd-hash>/<id>.jsonl`) | persisted on disk, survive process exit, survive the app being deleted |
| `sprite sessions list` + attach | **live exec/process** sessions (a running TTY) | ephemeral, gone when the process ends |

The app's chat UI **already speaks Claude's transcript vocabulary** — `stream-json` events and the on-disk `.jsonl` are the same `type: system/assistant/user/result` shape this code parses. So the sophisticated move isn't to rebuild a worse terminal or a worse picker. It's:

**Read Claude's own transcripts off the sprite and render them natively.** That gives you the `claude --resume` experience but *better*: native bubbles + tool cards, works on a fresh phone (history isn't tied to what this device persisted), and the session id it discovers is exactly what `--resume <id>` needs — which the chat already wires up.

1. **sessions/services path (primary):** A **Sessions browser** that enumerates `~/.claude/projects/*/*.jsonl` on the sprite → list with cwd + preview + last-used → tap → render full history natively → "Continue" sets `--resume <id>` + the matching cwd and drops you into the normal chat. This is the literal `claude --resume`-shows-history experience, native.
2. **websocket stream-terminal path (power tool):** keep the exec terminal, polished, for live/arbitrary TTY work and attaching to an in-flight run.
3. **In-flight reattach:** persist the running service name per chat; on reopen, rejoin the live log stream so a turn you walked away from keeps streaming (and even if the stream is gone, re-reading the transcript shows the finished turn).
4. **Demote ttyd** out of the primary nav.

## The idea

Two different "sessions" live on a sprite, and your two desktop commands hit each:
- `claude --resume` reads Claude's **transcripts** on disk (`~/.claude/projects/<cwd>/<id>.jsonl`) — persistent.
- `sprite sessions list` + attach reads **live processes** — ephemeral.

The sophisticated move isn't a WebView or a worse picker — it's that **the app's chat UI already speaks the same event format as Claude's transcripts**. So I made the app read Claude's own transcripts off the sprite and render them natively. You get the `claude --resume` experience, but *better*: native bubbles + tool cards, and it works even on a fresh phone because history lives on the sprite, not the device.

## What shipped (4 commits, pushed, `tsc` green)

1. **`claude-sessions.ts`** — scans `~/.claude/projects/*/*.jsonl` on the sprite (via a sprite-side node script, output sentinel-wrapped) and converts any transcript into the app's `ChatMessage[]`.
2. **`SessionBrowserSheet`** — lists every Claude session (preview · cwd · last-used), opens its **full native history**, and **Continue** resumes it via `--resume <id>` with the session's original cwd. Pull-to-refresh.
3. **Auto-sync on reopen** — `useChat.loadSession` now background-hydrates a resumed chat from its transcript when it's ahead of the local copy. That's the "close app mid-turn → reopen → see what happened" parity, sourced from the on-disk truth.
4. **Promoted/demoted** — the session browser (🕓 in the chat header + "Resume a Claude session" on Overview) and the renamed **Stream terminal** are now primary; **ttyd** is marked *legacy*. Guide + README updated.

The websocket stream terminal stays as the power tool — run `claude --resume` interactively, watch the live TUI, full shell.

One thing I couldn't verify without a device: the exact shape of the transcript JSONL on your sprites (I built the parser to the documented format and made it tolerant of unknown lines). When you run it on a simulator/phone, the session browser is the fastest way to confirm parsing against your real transcripts — open it on a sprite that's had a few Claude runs.

Honest assessment: **medium difficulty if you accept a thin daemon on the remote; very hard if pure SSH directly from the phone.**

## What the app actually depends on

Only three Sprites API primitives:

```
PUT  /sprites/{name}/services/{svc}     → streaming NDJSON (runs Claude, collects output)
GET  /sprites/{name}/services/{svc}/logs → same, reattach to logs
WSS  /sprites/{name}/exec               → TTY over WebSocket
WSS  /sprites/{name}/exec/{id}          → attach to existing TTY
GET  /sprites/{name}/exec               → list running sessions
```

The `BASE_URL` and `EXEC_WS_BASE` are module-level constants in `api.ts`/`exec-poc.ts`. Session discovery (`claude-sessions.ts`) is just SSH-equivalent `cat` / `node` commands, run via the service API — so it'd work identically on any machine running the same daemon.

## The realistic path

Run a **thin open-source daemon** on the remote machine (one binary, `~200 lines`). It exposes exactly those five endpoints over HTTP/WebSocket, using `child_process` to run commands and `node-pty` for TTY sessions. You'd connect via HTTPS (nginx in front, LetsEncrypt cert, or a Tailscale funnel). Auth is a single bearer token you configure.

What changes in the app:
1. **Connection model**: instead of `spriteName → api.sprites.dev`, you'd have a connection with a `baseUrl` + `token`. The sprite list screen becomes a connections screen (could keep sprites alongside custom remotes).
2. **Parameterize base URLs**: `api.ts` and `exec-poc.ts` currently use module-level constants — factor those into per-connection config. Maybe 2-3 hours of refactoring.
3. **UI for adding a remote**: enter host + token, test connection — essentially a settings screen.

The session browser and chat UI need **zero changes** — they only use the abstraction layer.

## Effort breakdown

| Piece | Effort |
|---|---|
| Daemon (node/go, expose exec+services API) | 2-3 days |
| App: parameterize base URL per connection | 3-5 hours |
| App: connections manager screen | 1-2 days |
| SSH-based auth (key distribution, tunneling) | ← avoid; use token + TLS instead |

Total realistic: **3-5 days** for a working prototype if you build the daemon. The app side is less than a day once the daemon API contract is defined — because you already have all the UI.

Make the daemon match the Sprites service + exec API exactly (same paths, same NDJSON format). Then in the app, a "connection" is just `{ type: 'sprite' | 'remote', baseUrl, token }`, and every existing feature — chat, session browser, live attach, transcript hydration — works unchanged against both.
